# Codex operating agreement — LectureLoop

1. Read all `docs/*.md` and `README.md` before designing or writing application code. **Product requirements are not suggestions.** Keep lecturer–student interaction and human teaching central. This is not a chatbot.
2. Single-agent implementation. Work incrementally through `docs/IMPLEMENTATION.md`; make all core paths real, integrated, and testable. Do not substitute mock buttons, static fabricated AI responses, or fabricated successful processing states.
3. Routine framework details, package choices, visual styles, error messages, and file boundaries are delegated to Codex within the documented stack. **Ask the owner only when a requirement is materially ambiguous, infeasible, conflicts with another confirmed requirement, or requires credentials/legal permission.** Describe the issue and give a recommendation; otherwise decide pragmatically and document the decision.
4. No microservices/Kubernetes. All application services, Postgres, background worker, and reverse proxy run via Docker Compose on one VM. Outbound calls to configurable AI APIs are allowed. Application media is stored on VM persistent volumes behind authenticated access.
5. Never put OpenAI keys in the browser. Backend is authoritative for role permissions, anonymity, visibility, poll lifecycle, questions, ingestion status and state transitions. WebSockets are a propagation mechanism; Postgres is truth.
6. Honor **course isolation** and private-vs-anonymous protections: no stored requester identity for anonymous questions; no learner-facing leak of private question text, membership, or counts; anonymous author cannot later edit/delete; teacher can moderate; named author can edit/delete. Lecturer-only grouping may consider private + public questions.
7. Keep AI model/provider configuration externalized behind clear text, embedding and transcription adapters. Implement actual OpenAI adapters first; document extensibility for local/other providers without building unused complexity.
8. Lecturer can teach without interacting with an AI console: slide presenter, mic and optional recording, automatic topic awareness/polls, low-friction questions. AI doesn't automatically publish unverified recording excerpts as certain; use transparent statuses and corrections.
9. Include responsive, keyboard-accessible and mobile-first student screens, visible loading/error states, useful retry actions, and simple UI, inspired by clean educational tools rather than clone-specific branding.
10. Maintain tests for core logic and permissions. Run migrations, backend/frontend checks and E2E smoke tests after major milestones; report genuine blockers and remaining work in `docs/PROGRESS.md`.
11. The deadline matters: build runnable core first, add remaining committed features progressively, never sacrifice data privacy or secretly degrade to simulation. Do not focus on CS50 demo until the product works; afterward create optional prepared replay fixture with clear disclosure.
12. Do not use any copyrighted university lecture recordings without suitable authorisation. External demo data must be permissioned / licensed and credited; never ship third-party material in git by default.

13. Any change to AI behaviour (including OCR/chunking, prompts, retrieval, provider inputs, storage, visibility, timeouts or user interactions) must update `docs/AI_WORKFLOW.md` in the same change. It is the canonical implementation reference; `AI_WORKFLOW_REVIEW.md` is only a pointer.

14. Owner revision 2026-10-22: new direct questions/replies are named and course-public; preserve historical private/anonymous records. New feedback is named to lecturers and stays lecturer-only, including inferred questions. Only authors edit wording; lecturers moderate/delete. Post question auto-submits only after a complete warning-free empty preflight; matches/failures require confirmation. At most one live lecture per course.

15. Owner revision 2026-10-23: regex/lexical heuristics may support cheap checks, candidate recall or explicit last-resort fallback; they must not be the sole semantic interpretation/relevance solution. Feedback uses one strengthened model pass per attempt, not a second verifier call. Automatic grouping favours precision: uncertain/distinct teaching needs remain separate and all questions stay visible. Keep quality checks small and practical.
